The unexpected part

The second run wasn’t warm.

My first repeated Namespace job passed every test, but started with zero cached files. It rebuilt from scratch. A green run didn’t mean a cache hit.

What I changed
Added a cache-hit guard, then checked the files and compiler stats. The next warm run hit all 59 cacheable compiler calls.

One small product suggestion
Make “cache attached, but no reusable data” prominent in the job summary. Namespace documents onboarding misses; a visible cue would make the first experience clearer.

What’s real, and how I measured it +

These are actual GitHub Actions jobs, replayed in the browser at a compressed timescale. Selecting a scenario does not trigger CI or spend credits. Click a stage to inspect its recorded duration and source evidence.

Both providers built the same pandas revision using its locked Pixi Python 3.12 environment and Meson build, then ran two existing groupby test files with two pytest workers. Compilation also used two workers. Each job started with a fresh checkout, environment prefix, and build directory. Only downloaded packages and ccache outputs persisted.

The source edit only renames a local Python helper. It is not a Cython change or a bug fix. There is one measured run per condition, on different underlying hardware, so this is an exploratory experiment rather than a general speed benchmark. Job totals include checkout, apt setup, cache handling and uploads. Stage timing combines command measurements and GitHub timestamps; sub-second gaps are grouped into setup or finish.

The early cache miss is consistent with documented onboarding behavior; I did not verify its private generation lineage. The miss remains visible in this demo.
