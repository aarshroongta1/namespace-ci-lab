What the comparison shows

The Cache Volume configuration returned passing checks in 98s, compared with 142s on GitHub. That is 44s less waiting in this trial, including startup and setup.

The runner-only change passed the same checks, but took 248s. Its archive restored successfully; only 3 of 59 cacheable compiler calls hit, compared with 59 of 59 in the other configurations. Most native code was recompiled.

The cause of those misses was not isolated. The Cache Volume already contained outputs from previous Namespace builds. The 248s-to-98s difference is not a pure comparison of cache transfer speeds.

Method, logs, and limitations
This tests a bounded contributor workflow, not the full pandas CI matrix. It uses revision 717bcd3, the upstream locked Pixi Python 3.12 environment, and an editable Meson source build. The edit renames a helper in GroupBy.prod. Tests are test_reductions.py and test_groupby.py, with two compiler processes and two pytest workers.
Each job starts on a fresh runner with a fresh checkout, environment prefix, and build directory. Only downloaded packages and compiler outputs are cached. The GitHub and runner-only cases restore the same existing archive; the Cache Volume case uses a previously populated Namespace volume.
Times run from the shared workflow creation timestamp to each successful job completion. “Wait to start” includes dispatch and scheduling, not just provider queue time. Stage timings combine GitHub timestamps and measured command durations. Checkout, tool installation, uploads, and cache handling are included. This is one trial per configuration on different underlying hardware.
The experiment follows the customer concern in Framer’s CI story and DuckDB’s PR-validation story: reduce the time developers wait for checks while retaining their GitHub Actions workflow. It does not measure large-scale concurrency, reliability, or cost.
